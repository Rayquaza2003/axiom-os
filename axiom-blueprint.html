Operating System · Architecture Blueprint · Working codename — Axiom

An OS where AI is a system resource, not an app.

Building on a capability microkernel, Axiom reconsiders the operating system around the realities Windows, macOS, and Linux were never designed for: ubiquitous local AI, standing cyber threats, and a lifetime spent across many devices. This is the grounded architecture — what is buildable, where the hard engineering actually is, and what stays aspirational.

00

Six principles, then everything follows

Most of this OS is a single repricing: treat AI as infrastructure the same way we already treat the CPU. Once that mental model is fixed, security, the filesystem, the interface, and multi-device behavior all start to fall out as consequences rather than features.

  1. AI is a scheduler-owned resource, not an app. A privileged Neural Resource Manager allocates model compute the way the kernel allocates CPU time — with quotas, preemption, power budget, and capabilities. No app ships its own always-on chatbot; they request a capability from the system.
  2. Security by capability, not by approval dialogs. Apps can only do what a capability grant allows. There is no "any file" default. The permission prompt is a rare exception, not the seatbelt that holds the OS together.
  3. The filesystem is a relationship graph, not a folder tree. Files are content-addressed objects in a flat store, organized by tags, provenance, and project — paths are an optional view over it.
  4. Your devices are one computer. A trusted peer mesh treats your laptop, tablet, and phone as loosely coupled components of a single machine that roams state, shares resources, and routes input to wherever you're looking.
  5. The interface reshapes itself to intent. Workspaces are grouped by what you're doing, not by application type; a glanceable information layer floats above the work without owning the screen.
  6. Privacy is architectural, not a setting. Key material lives under keys only you hold; the local AI runs in a no-egress zone behind a system-level firewall on its own context.
01

The hard truths up front

Before any of this is worth reading, let's clear the table. These are the tensions a serious architect has to accept rather than paper over — each is solvable, but only if it's designed for from the first day.

Truth · microkernels

Microkernel IPC has a real cost. Every cross-server call pays context-switch and marshaling overhead. This is fine for a control plane (grant a capability, ask for a model), but it is the wrong path for zero-copy media and hot AI tensors. Axiom pairs capability IPC with shared-memory + batching across the hot path, and keeps only authority on the IPC — not bulk data. This is the classic production answer, and it's why QNX and seL4-class kernels run real systems.

Truth · "best of both"

You cannot merge Windows and macOS. You cannot fuse two kernels or two window systems, and you shouldn't try. Axiom borrows UX and API patterns — macOS's integrated coherence and system services, Windows's hardware breadth and management rigor — and delivers them on one coherent microkernel of its own. The honest promise is a single coherent story, not a hybrid of two.

Truth · immutable vs. evolving AI

An immutable core and always-changing AI models pull against each other. The OS core is sealed and verified at boot — but models and the semantic index are hot data that must update weekly. So Axiom separates the two: a read-only, signed core, and a mutable, code-signed model store with its own behavioral attestation and rollback. Immutability protects the platform, not the content that lives on it.

Truth · sensor indexing

"Index everything on your screen and audio" is a real power, compute, and ethical budget. Constant OCR + embeddings of live screen content drains battery and raises a genuine privacy question about what an OS is allowed to remember. Axiom rations it: embeddings are cheap and batched, indexing is opt-in per source, long-lived personal context lives encrypted under your key, and apps expose structured content to the index so the system doesn't have to blindly photograph everything.

Truth · local AI ceiling

NPUs are real but small. By 2026 an on-device accelerator is tens of TOPS — enough for small models, semantic embeddings, transcription, and lightweight assistants. It is not enough for frontier-scale models. The local core therefore guarantees defensive AI (search, context, summarization) entirely on-device, while anything beyond the on-device ceiling crosses the model egress boundary only with explicit, per-request user approval. That boundary is the honest firewall.

Truth · zero-knowledge vs. roaming

State roaming sends bytes off-device, and that tension is real. "Keys only you hold" and "pick up exactly where you left off on your tablet" only coexist if your keys roam with your identity, not with the cloud. The server becomes a scrutable relay that stores only ciphertext and metadata, cannot decrypt, and is audited. You must be honest that a minimal online component exists — the achievement is making it unable to read you, not pretending it isn't there.

Truth · device offload

Borrowing another device's NPU is latency-bound. Round-trip over Wi-Fi commonly exceeds what local inference costs, so cross-device compute offload only wins for batch and async work — "render this on my tablet's NPU overnight" — not for real-time rendering or live voice. The mesh is designed around async resource brokerage, not latency-sensitive borrowing.

03

The stack, in eight planes

Axiom is built as a vertical stack of isolated planes. The single red line is the trust boundary: only plane P0 is trusted. Everything above it — drivers, filesystem, AI, network — runs unprivileged, and no crash or compromise in one plane can take down the OS. Each numbered plane is a genuine ordering: lower planes serve the ones above.

P0

The microkernel & capability security

This is the plan's security foundation, and it is deliberately the most conservative, most proven layer. Axiom does not hand-roll a kernel from scratch — it builds on a verified-capability microkernel lineage.

Components

  • Capability space. Every object — a file, a pipe, a model instance, a GPU surface — is a node in a per-process capability space. Invocation requires holding a grant; there is no ambient privilege.
  • IPC + shared memory. Capability invocation carries authority; bulk data travels through shared-memory windows to keep control-plane costs off the media path.
  • User-space driver & FS servers. A GPU driver, a filesystem, or a network stack that crashes is restarted — the kernel and every other app continue. This is the literal payoff of "a driver bug can't take the OS."
  • Verified boot + sealed core. The trusted-computing chain measures P0 at boot; the sealed core is read-only, so the surface an attacker can poison stays tiny and measurable.
P3

The AI core: AI as infrastructure

This is the crown jewel and the honest reason this OS exists. Axiom gives the AI stack what CPU and memory have always had — a privileged owner that rations, schedules, and guarantees isolation — and surrounds it with a hard egress boundary.

Neural Resource Manager (the repriced resource)

  • Owns accelerators & model memory. All NPU/GPU time and model weights are allocated by one privileged server, in quota slices, like CPU time-slices.
  • Auto-selection & preemption. An app asks for "a model that classifies intent on-device, under 120 ms"; the NRM picks the smallest capable signed model, loads it, and preempts it when a foreground task needs the silicon. Background AI is power- and thermal-accounted, so the system doesn't melt for a background summarizer.
  • Model registry. Models are signed, layered (system + per-app), and rollback-safe — the immutable-core answer to "but models change every week."

Unified Semantic Index

Instead of filename search, Axiom continuously builds a local, encrypted, content-addressed index over files, application structure, screen context, and audio. Querying is natural language — "find the Q3 revenue chart I had open on Tuesday" — resolved by a local planner into the relationship graph plus a vector store. The keystone decision: apps are encouraged to hand the index structured content (titles, entities, timestamps) rather than forcing the OS to photograph and OCR everything, which keeps both power and privacy sane.

The egress boundary (privacy as a firewall)

Local models run in a no-egress zone. Any outbound network call — from any process — crosses a single system-level filter that classifies whether model context is leaving the device. Everything on-device stays on-device; only an explicit, per-request user approval opens a controlled path to a remote model or service, and even that ride is encrypted under your keys. This is a stricter, more general version of what chat apps should have had all along.

P2

The data plane: a relationship graph, not a folder tree

Folders force a single parent, a single answer to "where does this belong?", and they punish large, messy, real-world data. Axiom's storage is a flat, content-addressed object store with a relationship graph on top.

How it works

  • Content-addressed objects. A file is identified by its content hash plus metadata — the same shape as a version-control object and a content-addressable network at once. Duplication is free; nothing is "copied" in the naive sense.
  • Tags, projects, and provenance as first-class edges. A document can belong to the Q3-planning project, carry a finance tag, and remember "created from that meeting recording." The graph is the organization; paths are one optional view.
  • The semantic index reads the graph. Because the data plane is a database, the AI core queries it natively — natural-language search is a graph query plus a vector lookup, not a filename substring match.
  • Atomic snapshots & rollback. Every update is transactional; the system keeps a rolling snapshot ledger. An update or even a filesystem operation that fails rolls back to the exact prior state on next boot — "atomic updates" isn't a feature, it's the storage model.
  • Peer sync built in. Zero-configuration peer-to-peer replication to your own devices, encrypted end-to-end, is a data-plane service — no cloud middle-man required.
Reality · hierarchy is still a view people want

Some workflows genuinely want a folder ("put all the tax docs here"). The honest answer: the tree remains as an illustrated view over the graph — a saved query — never as the storage mechanism. You get both, and nothing silently requires one.

P4

The device mesh: one computer, many bodies

Continuity and Handoff generalize into a first-class OS service: a trusted peer mesh that treats every device you own as a loosely coupled component of a single machine.

What the mesh provides

  • Trusted device attestation. Devices join the mesh via your key material, not Bluetooth pairing menus. Trust is unconditional-per-device and revocable.
  • True state roaming. Because P5's session manager already snapshots app state, the mesh roams exact state — cursor position, undo history, scroll — not just synced data. Walk away from the desktop, and the tablet is where you left off.
  • Resource brokerage (async-first). "Render this on my tablet's NPU" is a brokered batch job, not a real-time borrow. The latency honesty from the hard truths is encoded in the protocol: offload only where the round-trip is cheaper than local compute.
  • Automatic failover. Wi-Fi drops and the phone's cellular modem is handed over by a system service, invisibly.
  • Universal clipboard & audio. Routing follows your active gaze/input device — copy on the laptop, paste on the phone, and audio follows the screen you're looking at.
Reality · the relay exists and is scrutable

True mesh transport across the internet needs a relay to find devices and carry ciphertext. The design's integrity comes from the relay being unable to read — all payloads are encrypted under keys only you hold, and the relay is audited. That's zero-knowledge honestly: an endpoint exists, it just can't see you.

P5

The session: an interface that reshapes to intent

The desktop/folder/start-menu model is a metaphor for a single-tasking, single-authority world. The session layer replaces the metaphor with intent — the interface reorganizes around what you're doing, not which application is on top.

Intent workspaces

A workspace groups apps, assets, notifications, and background services by project or intent. Sliding from Work to Gaming is a session operation, not a manual shuffle: background services for the old intent are suspended, notification policies swap, and the right assets (the Q3 deck, the codebase, the game library) come forward as one set. Because the data plane is a graph, a workspace is a saved graph query.

Dynamic information layers

Static widgets become glanceable, interactive layers composited above the working surface — live and out of the way, read at a glance without stealing focus. The compositor owns them, so they're coherent across themes and never crowd out the work.

Unified input pipeline

Voice, gaze, hand gestures, pen, and keyboard/mouse feed a single input bus that arbitrates by contact priority — the device you're actively touching or looking at wins. Switching is lag-free because it's one stream with one scheduler, not N half-integrated drivers. (Honest caveat: gaze and hand-tracking depend on the hardware actually having the sensors.)

The honest sequence implied by all of this: prove P0 → P1 as a secure, driver-isolated microkernel on real hardware; prove P3 (the AI core) as the differentiation, because it's the only plane that changes what an OS is; and let the rest — UI, mesh, data plane — ride on those two foundations. But this is the blueprint, and its job is the architecture, not the timeline.
